## Purpose

The user compared velella's one-line composer with Swiftcord v2's growing one (2026-10-17). They asked how many lines Swiftcord grows to, asked for its transitions to be copied in full, and asked that anything Swiftcord lacks but the official client has be done too. Their decisions (AskUserQuestion, 2026-10-17) are recorded as D1-D4 below. The project rule applies: a complete client, with no part left out without an ASK (project `CLAUDE.md`).

| Flow | On Return with attachments (D10): first the limits (below); a too-large result leaves the draft and the files in the composer and creates no pending row. | Slot request | `POST /channels/{channel_id}/attachments`, body `{"files":[{"filename":<original name>,"file_size":…,"id":"<process-wide counter>","is_clip":false,"original_content_type":<MIME>}]}` in OA A2's order (one file per request, OA A1). `original_content_type` is always sent (CU-5): `UTType(filenameExtension: originalExt)?.preferredMIMEType ?? ""`, `text/plain` for `message.txt`, `image/png` for a pasted image, the original MIME for a converted HEIC/JXR; the slot `filename` is the original file's name (the message entry's is the Modify-edited one). No MD5 header except for a converted HEIC/JXR (OA A39, A49). Response: `attachments[0].upload_url` and `upload_filename`; a missing entry is an error (OA A3). Retries (CU-10): transport errors, 5xx and 429 (with §17's waits) at most 12 times with backoff, no other status; 40005 maps to too-large (OA A18). |
| Upload host | `upload_url` must parse as `https://discord-attachments-uploads-prd.storage.googleapis.com/<path>?<query>` with no user, password, port or fragment, and no dot segments (D13a). Anything else: no request, the send fails with a typed error and a one-time notice. The transport's allow-list (Sources/Velella/Transport/AllowList.swift) gains exactly this host with any path and a query; `authorizedPrefix` is unchanged, so no Authorization can go there. |
| Upload | Preflight then `PUT upload_url` (D15a), body streamed from a handle the app opened (never read whole into memory, never through FFI as bytes), seeked to `start`, with `Content-Length = size − start`. Headers are a closed list built outside `Rest` by one function, in Safari's order (OA A40-A42): the preflight's `Origin`, `Sec-Fetch-Site: cross-site`, `Access-Control-Request-Method: PUT`, `Access-Control-Request-Headers` (lowercase, sorted, comma-joined: `content-type`, or `content-range,content-type`), `Sec-Fetch-Mode: cors`, `User-Agent`, `Referer`, `Sec-Fetch-Dest: empty`, `Content-Length: 0`, `Accept: */*`, `Accept-Language`, `Priority: u=3, i`; the PUT's `Accept: */*`, `Content-Type: application/octet-stream`, `Sec-Fetch-Site`, `Origin`, [`Content-Range`], `Sec-Fetch-Mode`, `User-Agent`, `Referer`, `Sec-Fetch-Dest`, `Content-Length`, `Accept-Language`, `Priority` (the probe orders `Origin`, `Content-Range` before `Sec-Fetch-Site`, A42); `Host`, `Accept-Encoding` and `Connection` are the transport's. No Authorization (the request type has no such field), cookies, X-Super-Properties or X-Discord-*; Swift refuses an upload whose header names fall outside the list. Progress at most every 50 ms, clamped to the size; cancellable. Resume per CU-3 (empty-body probe with `Content-Range: bytes */*`, a 308 `Range` accepted only as `bytes=0-N` with `N+1 ≤ size`, one counter of at most 13 attempts with backoff, 1 h per PUT and 30 s per probe). Over HTTPS the header order and `Accept-Encoding` are CFNetwork's and unmeasured (OA A44). |
| Transport | A new file-backed upload operation (URL, an opened-file descriptor verified as CU-6 says, closed header list, progress listener, cancel handle) that also sends the preflight, implemented in Swift on the shared session through `Exchange` with a 64 KiB response cap, redirects refused. ## Security review of CU (rev 1.4, pilotfish:security-reviewer) and dispositions

Fidelity baseline: velella identifies as the Safari web client, so every upload request is compared with Safari's XHR.

| # | Pri | Finding | Disposition |
|---|---|---|---|
| CU-1 | P1 | A fixed `message.txt` path collides across conversations and pastes, so one conversation could send another's text; the temp location is unspecified | Fixed in contract (CU Temp files): every synthesized file (`message.txt`, `image.png`, received file promises) goes to `FileManager.default.temporaryDirectory/velella-attachments/<UUID>/<name>`, written with `.withoutOverwriting`; it lives exactly as long as its queue entry (kept through a failed send awaiting retry; deleted with its directory on send success, removal, discard or conversation teardown); `velella-attachments/` is swept at launch.
